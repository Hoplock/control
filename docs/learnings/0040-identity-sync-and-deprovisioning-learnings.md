# 0040 — identity sync and de-provisioning — Learnings

## Summary
- **M28 extended** (one line): a lock, a quarantine *and the directory's deactivation* are standing denials applied above the engine. Release `v0.27.0`, MINOR; migration `0021` (`directory_links`, `directory_groups`, `idp_connectors.directory_claim`, a `north_principals` index). No `ext` signature changed. Answers `Hoplock/enterprise#26`, item 3.
- **The sink** (`internal/provision.Sink`, `ext.SyncSink`): per tenant, joined on `ExternalID` by a link row, never on the username; Control allocates the subject id (`dir-…`, no `:`). Safe for concurrent use: one id serialised, different ids concurrent, a group change exclusive of subject writes in its tenant.
- **Order:** an upsert applies only if its `UpdatedAt` (required, compared to the µs) is later than the last applied; else nothing, no record. `Active: false` = deactivation. `Active: true` lifts one only if later than both the last applied `UpdatedAt` and Control's deactivation instant. `DeactivateSubject` for an unknown id keeps it; the later create provisions deactivated. `DeleteGroup` keeps a tombstone; an older `UpsertGroup` changes nothing.
- **Errors:** `KindInvalid` (names the field, nothing applied, don't retry unchanged) · `KindConflict` (the `Username` is presented by another subject; never adopted) · `KindUnavailable` (applied and stands, revocations/publication unfinished, or stopping: **retry the same call**) · `KindInternal` (store failure, safe to retry).
- **A deactivation revokes, in order:** (1) commit + record + north-bound sessions, API tokens, outstanding SSH certs revoked in that transaction (next authorize = deny `subject_deactivated`); (2) live and scheduled grants via `access.Service.Revoke`; (3) pending grant requests via the cancel path; (4) `cache_invalidate` then `session_kill` for the subject, again one decision budget later if newly placed. Holder text, verbatim: `Your account was deactivated by your organisation's directory.` A repeat writes no second record and finishes the rest. Re-activation restores nothing.
- **Login:** a connector's `directory_claim` (CLI `identity connector-put --directory-claim`, refused with no sync registered) names the claim carrying `ExternalID`; a login through it reaches the provisioned subject, rewrites nothing, or is refused `federation.not_provisioned` (creates nothing). A deactivated subject is refused `federation.subject_deactivated` through every door, and its north-bound credentials stop authenticating.
- **Claim mapping:** directory attributes and `Email` (as `email`) are offered as claims, `Groups` (ids) resolved to `UpsertGroup` names and offered under the mapping's `groups.claim`; only what the mapping names counts (`Mapping.ApplyDirectory`). Reserved names dropped. A group is matched by its directory `Name`.
- **Records** (control stream, actor `identity-sync:<provider>`, no person, `provider` + `external_id`): `identity_sync.subject_provisioned` / `subject_updated` / `subject_deactivated` / `subject_reactivated` / `group_upserted` / `group_deleted` / `refused`; plus `grant.revoked`, `grant.request_closed`, `operator.revocation.published`. `PUT`/`DELETE` of a directory subject: `409 subject_directory_managed`.
- **Start:** once, after seal, before listeners; `Stop` before drain. A `Start` error, panic or >30 s is logged `ERROR` (`identity_sync_not_started`, `provider`, `kind`); Control serves; `GET …/extensions` row `started: false`, `start_error: <kind>`. An unreachable directory is not a `Start` error.
- **Key files:** `internal/provision/`, `internal/store/directory.go`, `internal/store/standing.go`, `internal/identity/{federation,mapping}.go`, `internal/decision/inputs.go`, `internal/httpapi/north/{inventory,extensions}.go`, `internal/daemon/{provision,identityctl}.go`, `ext/identity.go`.
- **NEXT:** the console (0044) and the E2E suite (0045) prompts now carry the directory subject and the de-provisioning scenario. Enterprise's sync is queued (see the PR).

## Details

### Decisions made, and where this phase read the prompt
- **M28 is extended, not paralleled.** Its register row, heading and the cost paragraph are revised in place, and a paragraph on the deactivation is added. M7 gains one sentence (the directory is a second door the mapping governs); M15's *disabled* sentence notes the identity point. §3 (`internal/provision`, decision, identity, north, daemon), §5.3, §6 ("The directory door"), §7 and §10 are revised in place.
- **The connector "routes" are the CLI.** The prompt says the connector routes accept and show `directory_claim` and that writing one with no sync is "refused with `400`". There is no north-bound connector route, and this phase adds none, so the writer is `hoplock-control identity connector-put --directory-claim`, which refuses with an error naming that no identity sync is registered. It hands the host's sections to `HostConfig` and seals the registry the way the daemon does (`openWithSync`), because a host may register its sync from its section. The claim is shown on `GET /api/v1/session/methods` (`directory_claim`, omitted when empty): a claim name is configuration, not a secret, and that route is the only connector read there is. The console prompt names it.
- **Step 4 of the revocation order runs inside step 1's transaction.** North-bound credentials and certificates are store writes with nothing to publish, so they commit atomically with the deactivation and its record, which carries their counts (`credentials_revoked`, `certificates_revoked`). It is run again on every call, so a retry is complete.
- **Retry delivery is durable, not inferred.** The link carries `invalidate_owed` and `deactivation_owed`; any later call on the id, including a stale or replayed one, delivers what is owed and clears the flag. Without it, a retried upsert (now stale) would never re-send the invalidation the first attempt failed to publish.
- **A group change re-derives on every change of name**, not only a rename: a group created after its members (their ids resolve to nothing until it arrives), a delete, and a re-create all re-derive. Re-derivation uses the active mapping, so it also carries a new mapping version to those members.
- **Group invalidations are bounded**: up to 64 members get one `cache_invalidate` each; more get one `cache_invalidate all` for the tenant, as a quarantine does, because thousands of events would push the tenant's log past its replay floor (1024) and resync every proxy.
- **Locks:** a subject call takes the tenant's directory-groups advisory lock *shared*, then its `ExternalID`'s lock, then the username's; a group call takes the groups lock *exclusive*. Per-member advisory locks were rejected: a 10,000-member group would exhaust the lock table. Federation's unlinked `provision` now runs in a transaction and takes the username lock, so a login and a sync cannot both find a name free.
- **A federated identity that resolves to a directory subject** (linked earlier through a tied connector, whose tie was later removed) authenticates it without rewriting it, rather than refusing: the person was already proven to be that subject.
- **Unknown ids for deactivate/delete record what they keep** (`subject_deactivated` with `provisioned: false`, `group_deleted` with zero members): they are applied calls. A delete of a group already deleted is a replay and writes nothing.
- **Reserved attribute codes are dropped, not refused**: refusing would block provisioning a person over one directory field. They reach neither the link nor the mapping.
- **`UpdatedAt` is required.** A zero time cannot be ordered against anything; it is `KindInvalid` on `updated_at`. The doc comment says so.

### What the next session must not rediscover
- The holder text is `access.DeactivatedByDirectoryReason`; `provision.DeactivatedByDirectory` aliases it, and the decision record's `reason` uses it. The actor prefix is `store.IdentitySyncPrincipalPrefix`, aliased as `provision.PrincipalPrefix`; `store.SubjectDirectory.DeactivatedBy()` builds the record's `placed_by`.
- A deactivation's standing record: `code: subject_deactivated`, `placed_by.principal: identity-sync:<provider>`, `reason_code` = directory's, `external_ref` = the directory's `ExternalID`, `reason` = the holder text.
- `Authenticate` now reads `Subjects().Standing` (one statement with the lock and link joins) instead of `Subjects().Get`.
- `Subjects().PresentedByAnother` and `DirectoryLinks().ByPrincipal` are the uniqueness reads. Uniqueness between subjects the directory does not manage is unchanged (an operator's `PUT` can still give two non-directory subjects one login name, and `GetByPrincipal` answers one of them). **Known gap:** an operator's `PUT` of a *non*-directory subject is not refused when it adds a login name a directory subject presents; the prompt scoped item 7 to the sink and federation.

### Measurements
- `BenchmarkAuthorize/fan-out` against 200 directory links (one in ten deactivated) in the joined table: ~0.96–1.12 ms/op on this branch versus ~1.02–1.09 ms/op on `main`, interleaved runs; +5 allocs/op. `TestAuthorizeLatencyUnderFanOut` p50 1.04 ms, p99 2.7 ms. `TestStandingDenialsCostTheDecisionPathNoRoundTrip` holds: four statements unchanged, three for a deactivated call.
- A deactivation's call takes about two decision budgets (~5 s at defaults) when it revokes grants: each grant revocation waits its settle pass (run eight at a time), then the subject's kill waits its own.
