# 0062 — CA custody through the key store — Learnings

## Summary
- **Resolution order:** a registered `ext.KeyStore`, else Control's software custodian over `credential.key_encryption_key_env`, else none (no CA: `503 ca_not_configured` north, `503 no_authority` south, `ca` commands error; all name both settings). One resolution, `daemon.buildKeyStore` → `keyCustody{store, name}`, handed to `buildCA` and `audit.NewRetentionKeys`; `ca show|rotate|issue|certificates` build it after `prepareExtensions` (they now call `HostConfig`). `TestTheCAAndRetentionShareOneKeyStoreResolution` (source test) holds it.
- **A key the resolved store does not hold** (NotFound, or another key under the name): `credential.CustodyError` / `ErrKeyNotHeld`; nothing signed, no other custodian asked. South `503 ca_key_not_held`; `GET …/ca` `500 internal`; `ca issue`/`ca show` exit non-zero naming `ca rotate`; start-up logs `ssh_ca_key_not_held` and starts.
- **A store that cannot be asked** (`ext.KindUnavailable`, `context.DeadlineExceeded`): `ErrKeyStoreUnavailable`, never read as absent. South `503 key_store_unavailable`; `GET …/ca` and `POST …/ca/rotate` `503 unavailable`; start-up logs `ssh_ca_key_store_unavailable`. Any other store error is a plain outage (500).
- **Custodian:** `ext.KeyInfo.Custodian` from the store's `Describe`, asked per call; `custodianOf` is gone. **No migration:** `tenant_ca_keys.private_ref` is the key's name in the store (`ssh-ca:<key id>`), as the code always wrote; 0007's comment was wrong and is left (forward-only), the Go doc on `store.CAKey` now says so. `tenant_ca_keys.private_key` is never written.
- **Key files:** `internal/credential/ca.go` (`CustodyError`, `Custody`, `bundle`, `describeKey`, `custodyError`, `WithKeyStoreName`), `internal/credential/credentialtest` (an in-memory `ext.KeyStore` for tests), `internal/daemon/{north,serve,identityctl}.go`, `internal/httpapi/{north/ca.go,north/server.go,south/errors.go}`.
- **North API stays `5`:** no new north code (a new one moves the version, and the console's Deployment baselines print it); south codes are conventions, not contract enums.
- **Release `v0.49.0`**, MINOR, `### Breaking`. No decision added; PLAN §3, §6, §7, §10 revised in place. Owes `hoplock/enterprise` a sync; `hoplock/proxy` none.
- **NEXT (0063):** algorithm plumbing lands on this custody: `CA.algorithm` is generated by the resolved store, so a new `ext.KeyAlgorithm` must be one the registered store can make, and `describeKey`/`signer` compare SSH wire encodings of the public half.

## Details

### What was there

`buildCA` built `extdefault.NewSoftwareKeyStore` over the KEK and nothing else,
so a host's `ext.KeyStore` held only retention keys, and a host with a key store
but no KEK had no CA. `CA.Describe` named the custodian with `custodianOf`,
which read it off `private_ref` — but `private_ref` always held
`ssh-ca:<key id>`, so it always answered `"software"`, true or not.

### Decisions this session made, and why

- **`buildCA` takes the key store; it no longer builds one.** The only way two
  resolutions can disagree is if two places resolve, so the fix is structural:
  `buildKeyStore` is the one constructor (the source test fails if anything else
  calls `extdefault.NewSoftwareKeyStore` or `(*ext.Extensions).KeyStore`, or if
  a function hands `buildCA` or `NewRetentionKeys` anything but its own
  `buildKeyStore` result, or resolves twice). `keyCustody` carries the store's
  operator-facing name (`registered ext.KeyStore <provider[@version]>` or
  `Control's software custodian`) so every refusal says which store was asked.
- **`Describe` asks the store; the bundle does not.** `bundle` (lifecycle rows
  only) serves `Verify` and `IssueForSession`'s trust bundle: what a target
  trusts is public, and an HSM round trip per issuance for a diagnostic would be
  waste. `Describe` (`GET …/ca`, `Ensure`, `Rotate`'s result) asks the store for
  the active key, so it never states a custodian the store would not confirm.
- **A store holding a different key under the name does not hold the key.**
  `signer` and `describeKey` compare the store's public half with the row's.
  A signature from another key would chain to nothing a target trusts — or to
  something it trusts for another reason. Cheap: `crypto.Signer.Public()` is
  local.
- **`GET …/ca` answers a 5xx for a key the store does not hold**, rather than
  `200` with a custodian it cannot confirm. `POST …/ca/rotate` and
  `GET …/ca/certificates` need nothing from the private half and keep working:
  rotation is the way out.
- **Start-up logs and starts.** `north.Server.Ensure` turns a `CustodyError`
  into an `ERROR` line for the configured tenant and returns nil. Policy, the
  console and audit work without the CA. Nothing rotates on boot. A first-boot
  generation that fails for any other reason is still fatal, as before.
- **No new north-bound code.** API-VERSIONING says a new code moves the
  version; moving it to 6 changes `ui/e2e/baseline/deployment-*` ("5, answering
  1 to 5"), which can only be regenerated in CI's renderer. So: unreachable is
  the existing `503 unavailable` ("cannot serve right now and will on a
  retry"), not-held the existing `500 internal`, each with a message naming the
  key, its ref and the store; no parameter added to either. If a later phase
  wants machine-readable codes here, it moves the version and retakes those
  baselines in the same PR.
- **South-bound codes are new conventions** (`ca_key_not_held`,
  `key_store_unavailable`, both 503 beside `no_authority`). `code` is a free
  string in the contract and `enums.go` says these are this server's
  conventions; the proxy treats every non-200 identically.
- **`ca show` prints, then fails.** It lists every bundle key with its
  custodian — retired keys on their own lines (`retired key: …`), which
  `deploy/target/entrypoint.sh`'s `^ssh-` grep ignores — prints the bundle, and
  exits non-zero when the active key is not producible, naming `ca rotate` (not
  held) or "nothing is signed until the key store answers" (unreachable).
- **`private_ref` settled in code, no migration.** A custodian column would be a
  second source of truth beside the store's own answer, and with no installed
  base there is nothing to backfill. `tenant_ca_keys.private_key` (0007) is
  dead: the software custodian writes `software_keys`. Dropping it is a
  forward migration nobody needs yet — recorded, not done.

### Found, not fixed

- **The software custodian's ciphertext is still not bound to its row** (0024's
  finding). For the CA it matters no more than for retention: a swapped-in
  ciphertext decrypts to a key whose public half is not the row's, and
  `signer` now refuses that as "not held" before anything is signed — so the
  swap is caught for the CA, not just harmless. Not built.
- **The console's fixture host** (`ui/e2e/fixture/host`) registers `e2e-keys`
  in memory, so its CA now lives there; a run over a database from an earlier
  run meets a stranded key, which start-up logs. No screen reads the CA.

### Verified by hand

On a fresh database (migrate, seed, server with a KEK): `make conform` 58/58,
the `brokered` group's five issuances among them. `ca show` over a stranded
key printed:

```
  active key: 20261119-… (ed25519, custodian NOT HELD: the key store, Control's software custodian, does not hold tenant acme's CA key 20261119-… (ssh-ca:20261119-…), created …)
```

then the bundle, then exited 1 naming `ca rotate`.

### Cross-repo impact

`hoplock/enterprise`: its `ext.KeyStore` must now generate, sign with and
describe Ed25519 keys named `ssh-ca:<generation>` per tenant (beside
`audit-retention:*`), keep a retired one through the rotation overlap, answer
`KindNotFound` for an absent key and `KindUnavailable` when it cannot be asked,
and state a truthful `KeyInfo.Custodian`. A CA key made in Control's software
custodian before its store was registered is refused — a fixture or development
database. `server.Main`'s and `Options.HostConfig`'s doc comments now name every
subcommand that calls `HostConfig`. `hoplock/proxy`: none —
`POST /v1/credentials/certificate`'s shape is unchanged.
