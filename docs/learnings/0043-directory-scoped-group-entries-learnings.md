# 0043 — directory-scoped group entries — Learnings

## Summary
- **Release `v0.30.0`, MINOR, no `### Breaking`; no migration; no `ext`/`server` change.** M7 revised in place; register unchanged. Answers `Hoplock/enterprise#51`, item 2.
- **Keys:** `directories: [<source>…]` on a `groups.map` entry (0042's source pattern); `groups.require_directories: true`. `schema_version` stays `1`. A group named N from source S matches the entry listing S for N, **instead of** (never as well as) the unscoped entry for N; else the unscoped one unless required; else nothing. **Logins match unscoped entries only.** No wildcard.
- **Rejections:** `mapping.directory_name` (`groups.map[i].directories[j]`), `mapping.directories_empty` (`directories: []`), `mapping.directory_duplicate` (a source twice for one `external`, names the first entry). Two unscoped entries stay `mapping.group_duplicate`. `mapping.too_large` counts a scoped entry once per listed directory.
- **Recalculation (`provision.Recalculator`):** every mapping write, scoped or not, reaches every directory subject by itself, **with no sync**: a subject whose row names another version is stale; batches of 200 in subject order, the sink's lock order and `derive`, invalidations after each commit as a group change sends them (per subject, or one tenant-wide past 64). No session ended. At once on the node that took an API `PUT` (which never waits); else within a minute by the sweep. Records `operator.claim_mapping.applied` (`after`=version, `recalculated`, `changed`, `complete`), actor = the version's stored author (`cli` from `mapping-put`).
- **Deviation (user's choice):** the sweep walks **the tenants this process has seen** (configured, proxy subscriptions, mapping read/written, sync calls), not a store read listing tenants: the store cannot list tenants (M18). So a CLI-written mapping for a tenant no node has seen waits for that tenant's first proxy.
- **Read/record:** `GET …/identity/claim-mapping` + `directories` (sorted), `require_directories`, `stale_directory_subjects`; `groups` includes scoped entries'. Decision record subject `directory_source` (omitempty), explain `mapping.directory_source`. Decision path: no new statement.
- **Key files:** `internal/identity/mapping.go`, `internal/provision/{recalc,subject,deliver}.go`, `internal/store/directory.go` (`Stale`, `StaleCount`), `internal/daemon/{serve,grants,identityctl}.go`, `internal/httpapi/north/{ca,inventory,server}.go`, `internal/decision/{inputs,record,explain}.go`.
- **NEXT:** Enterprise's sync is queued (see the PR). Prompts 0046, 0047, 0048 carry this phase's fields. A rolling upgrade must finish before a scoped mapping is written (older builds read it as unparseable: an outage, never unscoped).

## Details

### Where this phase read the prompt
- **The tenant sweep (user's decision, recorded as a deviation).** The prompt asked for a store read of "the tenants with any stale directory subject". The store cannot list tenants: every repository method names its tenant (`TestRepositoryMethodsTakeATenant`), and PLAN §3 says the grant poller, the configuration announcer and the archive feed each walk "the tenants this process has seen" for that reason (M18). Asked, the user chose to keep that rule. So the third read is gone, and `Recalculator.Track` is told of the configured tenant at start, each tenant a proxy subscribes in (`trackSubscriptions`), each whose mapping is read or written on the north-bound surface, and each the sink is called in (`provision.Options.Track`). Every tenant a decision can be taken in has a proxy, so every tenant where a stale subject could decide anything is swept by the nodes holding its streams. PLAN §6 and §3 say this in the present tense.
- **The sweep's per-tenant check is two reads and no transaction**: the active mapping row's version, then `Stale(…, limit 1)`. Only a tenant with something stale opens a batch transaction, which re-reads the mapping (parsed, so an unreadable one fails the batch as an outage, M11) under the shared directory-groups lock.
- **A run also delivers invalidations owed and not delivered.** `Stale` returns a link that is stale **or** owes a cache invalidation that is not a deactivation's (`invalidate_owed AND NOT deactivation_owed`). Without it, a batch whose publication failed would leave its subjects current and their invalidations owed with nobody to deliver them. The cost is that a sink call's own owed invalidation, in the moment between its commit and its delivery, may be published twice; `cache_invalidate` is idempotent. `stale_directory_subjects` counts version staleness only.
- **Records per version, not per run.** A run that applies two versions (a mapping written mid-run) records each: the superseded one with `complete=false`. A run that recalculated nothing records nothing. A stopped run still records its count (`context.WithoutCancel`, 10 s).
- **Actor.** Both `operator.claim_mapping.applied` and the run's `operator.revocation.published` records have the version's `created_by` as `principal_id` (the API stores the writer's subject; `mapping-put` stores `cli`); `claim-mapping` if none is stored.
- **`derive` is a package function** taking the provider from `link.Provider`; `recalculate(ctx, tx, tenant, link, mapping, skipCurrent)` is the one way a subject is recalculated without a call on it — `rederive` (a renamed group, `skipCurrent=false`) and the Recalculator (`true`) both use it. Delivery is `publisher.invalidate`, shared by `deliverGroup` and the Recalculator; its errors are typed (`*recordError`, `*settleError`, else the stream's) so `deliverGroup` classifies them as before.
- **`ApplyDirectory(source, attributes, email, groupNames)`** no longer offers groups as a claim; it matches each name itself. An attribute named like `groups.claim` is still never read as a group list (tested).
- **`Mapping.Author`** is set by `identity.ActiveMapping` from the stored row.
- **CLI:** `mapping-put` names listed sources with no link or group in the tenant (`HasSource`), as a line and never a refusal, then says the server recalculates; `--dry-run` opens nothing. `mapping-show` prints the stale count.
- **No index added.** Plans with 20 000 analysed rows over ten tenants and only `directory_links_subject_key` left on `directory_links` (`TestTheStaleReadsAreServedByIndexes`):
  ```
  batch:  Limit -> Merge Join (d.subject_id = s.subject_id)
            -> Index Scan using directory_links_subject_key  Index Cond: tenant = $1 AND subject_id > $2
            -> Index Scan using subjects_pkey                Index Cond: tenant = $1
  count:  Aggregate -> Hash Join
            -> Bitmap Index Scan on subjects_pkey               (tenant = $1)
            -> Bitmap Index Scan on directory_links_subject_key (tenant = $1)
  ```
  Both read the tenant's prefix of each index, so a tenant with nothing stale costs one pass over its directory subjects per sweep per node. Revisit with a partial index only if that shows up.
